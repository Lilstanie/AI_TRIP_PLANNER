# Agent Note: Trip 交互对齐规格与工单草稿

Status: proposed

## Problem

PR #782 已经把同一 Trip 的多个 Chat、地图和五个操作入口放在一起，但主要完成了页面
结构。用户仍不能顺畅地在聊天、事实修改、行程编辑和日历之间完成操作。需要依据真实
Mindtrip 交互完善现有 PR，而不是另起一个相似界面。

用户于 2026-10-29 批准本规格和九票结构，授权发布 GitHub/Jira 并按 implement-spec 并行实现。
实现和验收完成前，本文仍保持 proposed；PR #782 不合并。
事实依据见[Mindtrip 交互参考](../../../../docs/design/mindtrip-interactions.zh.md)；
差距及证据边界见[对照分析](2026-10-29-mindtrip-interaction-alignment.md)。
已有[Trip 首页操作决策](../../implemented/feature/2026-10-29-trip-home-actions.md)中的
原位聊天、最新 Plan、返回焦点和多 Chat 关系继续有效。下述日历、编辑和手机输入框方案
获批并实施后，需要同步更新旧决策中的只读及布局条款。

## Proposal

### Problem Statement

旅客打开一个 Trip 后，希望边聊边查看地图、修改事实、编辑行程和查看排期。
当前输入需要二次发送，事实标签无法直接修改，Trip 首页的行程和日历主要只读，
桌面面板也不能展开。用户需要围绕同一 Trip 完成任务，并始终知道如何返回。

### Solution

保留现有 Trip 与多个 Chat 的关系，完善同一个工作区：中间是聊天列表或当前对话，
右侧保留地图和五个操作入口。左侧主入口改为 New chat，允许只聊天而不创建 Trip。
Trip 首页移除 Start chat 按钮，直接展示聊天输入框，首次发送才创建关联 Chat 并发送第一条消息。
正在生成的请求属于发起它的 Chat，而不是当前可见页面；离开页面后继续，返回后可看到进度或结果。
事实芯片各自打开编辑器。Itinerary 在右侧直接编辑，Calendar 支持周时间轴和月历，
点击活动进入同一个编辑流程。桌面面板可以展开为内容与地图并排，手机沿用既有导航，
操作面板全屏，底部输入框保持可用。

### User Stories

1. 作为旅客，我希望一个 Trip 中显示所有关联 Chat，以便分别讨论餐饮、景点和出行。
2. 我希望看到 Chat 数量、可区分的主题标题、日期或消息摘要和进入方向，以便辨认不同对话。
3. 我希望打开 Chat 后保留 Trip 地图和操作入口，以便继续处理行程。
4. 我希望首页输入后即可创建关联 Chat 并发送，以免重复操作。
5. 我希望 Shift+Enter 换行，中文输入法确认时不发送，以便准确组织问题。
6. 我希望发送失败时保留消息并能重试，以免丢失输入或创建重复 Chat。
7. 我希望底部输入框在聊天列表很长时仍可用，以便随时开启新讨论。
8. 我希望切换 Trip 时不会把未发送内容误发给另一 Trip。
9. 我希望分别点击目的地、日期、人数和预算进行编辑，以免寻找无关表单。
10. 我希望偏好列表与四项事实分开管理，并沿用保存和重新规划的明确区别。
11. 我希望直接在右侧修改活动时间和地点，以免离开 Trip 上下文。
12. 我希望在右侧将活动移入 Ideas、重新排入某天，并撤销最近编辑。
13. 我希望行程、日历和地图反映同一个最新 Plan，以免看到互相矛盾的安排。
14. 我希望打开旧 Chat 不会覆盖 Trip 的较新 Plan。
15. 我希望以周时间轴查看每天活动和住宿，以便理解日程的时间关系。
16. 我希望切回月历查看整个 Trip 的日期，以便快速定位某天。
17. 我希望点击日历中的活动后进入对应编辑，以免再次查找活动。
18. 我希望地图与选中的日期或活动一致，以便核对位置。
19. 我希望展开右侧内容并同时看到地图，以便处理较复杂的行程。
20. 我希望关闭或收起面板后回到原位置，保留当前 Chat 和待编辑内容。
21. 我希望手机保持熟悉的导航，输入框和保存按钮在小屏幕上可操作。
22. 我希望用中文、英文或键盘操作都能完成同一流程。
23. 我希望没有时间、地点或供应商结果时看到诚实的空状态，而不是编造的数据。
24. 我希望请求尚未完成时切换上下文不会把旧结果写进另一个 Trip。
25. 我希望左侧 New chat 可以开始普通聊天，不必先建立 Trip 或填写出行事实。
26. 我希望 Trip 首页没有单独的 Start chat 步骤，首次发送才创建关联聊天。
27. 我希望离开对话查看 Trips、Calendar、地图或设置时，原 Chat 的生成继续。
28. 我希望切回仍在生成的 Chat 时继续看到进度，切回已完成的 Chat 时看到完整结果。
29. 我希望只有主动停止时才取消生成，停止后保留已有内容并提供明确状态。
30. 我希望首页 Itinerary 和右上角 Trip 是同一个编辑视图，修改后两处立即一致。
31. 我希望地图供应商失败或屏幕尺寸变化时，工作区仍可操作，不因地图清理而崩溃。

### Implementation Decisions

- 左侧主按钮显示 New chat，并执行通用空 Chat 创建流程；不是只替换 New trip 的文案。
  普通聊天可以一直没有 Trip 关联，不创建空 Trip，不把填写行程事实作为聊天前提。
  Trips 页保留明确的新建行程入口；只在旅客进入规划流程并产生可保存 Plan 时关联 Trip。
- 使用现有 Trip、Chat、Plan、活动身份及编辑操作，不新增平行的排期数据源。
- 同一 Trip 的聊天切换继续原位发生；不复制 Mindtrip 的 Chat URL 跳转模型。
- 首页非空输入执行一次创建／选择关联 Chat 和一次发送。重复提交不得复制 Chat 或请求。
  Trip 首页不显示 Start chat 按钮；聊天框拥有发送操作，首次非空发送才创建关联 Chat。
  仅聚焦、输入、切页或清空不创建 Chat；空消息不创建 Chat，也不发请求。
- 发送失败保留原 Chat 和可恢复输入；重试复用该 Chat。中文组合输入确认不发送。
- 切换上下文前刷新待保存内容，但不把页面离开或 Chat 切换等同于取消请求。
  普通导航、打开面板及桌面／手机断点切换均不应静默停止生成。
- 同一浏览器工作区存活期间，生成任务、流式进度、部分回复、完成结果和错误归属于
  发起请求的 Chat。切到另一个 Chat 或 Trip 后，原请求继续写回原 Chat；当前页面不接收其回复。
  返回原 Chat 时呈现正在生成、已完成、失败或主动停止的真实状态。
- 只有明确 Stop、删除所属 Chat／Trip 或退出账户等真正终止任务的动作才取消；
  页面关闭或完整刷新后的后台持久执行不在本期保证范围内。
  同一 Trip 的规划请求继续遵守既有并发约束，不因后台生成引入并行改写同一 Plan。
- 请求返回时核对所属 Chat、Trip 和 Plan 版本。若原 Trip 已被手动编辑或更新，保留回复并
  明确提示 Plan 无法直接替换，不得覆盖新 Plan，也不能以防串写为由静默丢掉整个回复。
- 四项事实复用现有字段校验、币种解释、保存及重新规划规则。保存不等于自动重新规划。
  Trip preferences 管理偏好列表，人数和预算等事实有自己的入口。
- Trip 首页 Itinerary 与对话右上角 Trip 使用同一套行程编辑视图和数据来源。
  两个入口共享最新 Plan、活动身份、选中天／活动、待保存编辑及 Undo 记录；从任一入口
  修改或撤销后，另一入口、Calendar 和地图立即一致，打开旧 Chat 也不能降级 Plan。
  复用现有编辑／预览／确认流程，不维护一个只读副本加一个可编辑副本。
- Calendar 默认周时间轴，允许切换月历；仅覆盖当前 Trip。周范围导航不离开 Trip。
  跨月及跨年日期使用现有日期语义，不能因浏览器时区偏移一天。
- 有有效起止时间的活动显示在时间轴；无时间活动和住宿有独立区域，不编造时刻。
  同时段活动必须都可发现和操作，不能相互遮盖；住宿不重复算作每日活动。
- 日历活动通过稳定身份连接原活动，点击后定位对应天和活动，进入同一行程编辑器；
  月历日期仍可打开对应天。缺少可编辑身份时提供只读详情，不能编辑错误活动。
- 周／月切换保留当前日期；编辑后继续显示原选中天。跨周、跨日及同名地点均按身份关联。
- 桌面默认窄抽屉，展开为内容与地图并排。关闭恢复原 Chat、页面滚动及触发控件焦点。
  手机采用全屏操作面板，不改变现有全局导航，也不引入 Up Next 分区。
- 地图事件订阅／清理遵循对应渲染器的返回契约；失败回退时移除旧错误层和失效控件。
  加载失败不阻断聊天及行程；切换 Trip、页面或断点不因卸载地图而使工作区崩溃。
- 使用既有语义颜色、焦点和减少动态效果规则；不引入 Mindtrip 品牌、素材或回复原文。
- 继续更新 PR #782，不合并；GitHub ticket 与 Jira TP story 一一对应，编号创建后填写。

### Testing Decisions

- 首选现有真实浏览器工作区 E2E 入口，从行程卡片进入 Trip，避免仅测孤立按钮或函数。
- 在实现前记录失败清单，覆盖创建／发送／重试、上下文切换、旧快照、重复提交及输入法。
- 以可控的延迟流复现：发送后离开 Chat，分别查看 Trips、Calendar、设置、另一个 Chat
  或另一个 Trip；控制任务在离开期间完成，返回后核对回复仅出现一次、内容完整、状态正确。
  同时验证仍在生成时返回、主动 Stop、失败重试、期间手动编辑及旧结果不能覆盖新 Plan。
- 点左侧 New chat 后发送普通聊天，只增加 Chat，不创建 Trip，也不强制打开出行事实表单。
  Trip 首页没有 Start chat；单纯聚焦／输入不创建 Chat，首次发送只创建一次。
- 从首页 Itinerary 修改活动，再从右上角 Trip 查看；反向修改及 Undo 也在两处同步，
  Calendar 与地图使用同一活动身份；覆盖旧 Chat 快照和待保存切换。
- 模拟 Google 加载失败及回退、反复卸载地图、切换桌面／手机断点，验证不崩溃、
  旧错误层不残留，并且聊天和行程仍能操作。
- 复用行程编辑、排入 Ideas、撤销及地图定位的既有浏览器验证，不建立第二套测试运行器。
- 行程包含两个以上 Chat、旧 Chat 快照、空列表、长标题、待保存内容和进行中的请求。
- 日历包含跨月、跨年、无时间活动、重叠时间、空天、住宿、同名地点和超出一周的 Trip。
- 检查桌面、平板和手机，以及 520/521、1000/1001 边界、缩放、中英文和减少动态效果。
- 检查键盘、关闭后焦点、手机浏览器返回优先关闭面板、无水平页面溢出和输入框可见性。
- 使用明确隔离凭据的模拟服务，拦截外部请求；截图、断言及失败结果形成可复跑证据。
- 现有 action-rail 脚本的基线失败需要先分类及修复原因，不能删断言或延长超时掩盖问题。
- 模拟浏览器结果不代表真实供应商、生产登录或真机键盘／安全区域已验证。
- PR 描述绑定最后代码树与实际运行结果；未运行、失败或跳过均明确标注。
- 每个切片完成后执行 `/review-trip-planner`，审查对应固定比较点与需求；最终对 PR #782
  完整集成 diff 做独立 Standards 和 Spec 两轴审查，分别报告，不以 CI 成功替代审查。
- Ponytail full 同时作为实现约束与审查门槛：优先复用现有编辑器和状态，检查正确性、
  数据安全及重复实现；单独报告，不替代 Spec／Standards，不删减校验、错误处理或无障碍。
- 审查发现项有具体场景、路径和证据；区分原 PR 缺陷、已有集成风险和后续新需求。
  修复后复跑受影响检查并审新增 diff，最终结论绑定最后 head。审查不自动发布评论或合并。

### Out of Scope

拖拽改变时间；Media、Receipts、分享协作和语音；照搬手机 Up Next；跨设备页面恢复；
新供应商接入或与本交互无关的数据模型重构；完整页面刷新、关闭浏览器后仍后台生成的
服务端任务系统；本轮自动合并。已有预订展示保留，不新增真实下单流程。
实现生成状态归属所需的局部状态调整在范围内，不新增另一套 Trip／Plan 模型。

## Alternatives considered

- 只修改间距和卡片：无法解决二次发送、只读排期及上下文切换问题。
- 新建一套首页行程编辑器：会让预览、校验、Undo 和最新 Plan 规则分叉。
- 保持切换 Chat 就取消生成：不符合用户离开页面后回来继续查看回复的要求。
- 原样照搬全部功能：媒体、分享、语音等缺少获批的产品模型，本期排除。
- 新开相似 PR：用户明确要求继续改善现有 PR #782。

## Acceptance criteria

- 用户审阅并批准完整 spec 与九个切片后，才发布及实现。
- 发布后每张 GitHub ticket 有对应 Jira story，阻塞关系可见。
- 原位多 Chat、最新 Plan 和已获批六项交互均有端到端验收证据。
- 最终更新 PR #782，未经用户明确指令不合并。

## Risks

- 同一 Plan 在多 Chat、行程编辑及日历中被修改时，需要保持现有版本一致性。
- 行程编辑器可能依赖专用页面上下文；复用时必须保证预览、Undo 和地图都可达。
- 手机底部输入框与键盘、面板及页面滚动之间的关系需要真实浏览器几何验证。
- 模拟视口无法证明真实设备输入法、安全区域或线上供应商行为。
